# Twitter UI 二次开发代码规范

本规范仅约束 Twitter UI 二次开发过程中**需要修改 / 重构 / 新增**的局部方法与模块，不要求变更 Misskey 原始项目中已有代码。组件与状态层若与现有 Misskey 基础组件架构冲突，以现有基础组件架构为准（裁定见文末附录）。

## 通用规范

1. 各函数（包括闭包、回调、类型别名、接口、枚举 / const 对象）均需加入中文 JSDoc 风格注释（排除类型标注字段），以描述方法 / 类型作用及所在数据链角色。
2. 各函数（包括闭包、事件 handler）、变量、导出类型需加入严格 TypeScript 类型标注，禁止隐式 any。
3. 枚举或 const 常量对象中各项需加入对应的中文注释；优先使用 `as const` 字面量对象，除非需要枚举反向查找。
4. 文件顶部需加入注释块，以详细描述文件所属领域、作用等基础信息。
5. 使用标准 src-layout 方式编排文件，分层存放领域模型、适配器、状态、组件、页面、路由、引导启动模块。
6. 不允许跨模块直接引用内部实现文件（`*.internal.ts`），模块对外 API 需通过模块索引文件（`index.ts`）顶层暴露。
7. 对于预期中形态稳定业务类型 / 业务方法实现，不允许额外抽 interface 抽象封装，以避免过度设计。
8. 允许对预期中形态不稳定，但接口不变的适配器 / 外部对接实现使用 interface 抽象封装，以保持对外接口稳定。
9. 尽量避免造成悬空配置项、悬空 computed、未使用工具方法与常量。
10. 同一业务概念只允许一个权威类型，禁止复制枚举、状态字段或类型投影，再依靠测试维持一致；权威类型统一放置在 domain 目录，只读视图投影允许从权威类型派生。
11. 环境配置加载、环境探测、前端 readiness 和制品身份由 Bootstrap 模块负责，业务域、组件、store 只接收冻结的业务策略、依赖参数和不可解析运行身份，不得导入或解释运维探测实现与探测结果。
12. 权威事实只能单向派生，接口原始响应、视图 DTO、表单视图、路由序列化字段不得反向参与业务决策；业务实例事实不得在组件、路由守卫中重复定义。
13. 兼容代码必须对应真实存量接口、本地持久化数据或存量用户，并明确移除条件，否则不得新增；修改现有兼容路径时不得扩大其能力或消费者范围。
14. 配置项不得用于切换新旧内部业务架构，协议版本应属于接口请求 Schema，而不是前端运行时实现开关；feature flag 仅用于 UI 灰度展示，不可修改领域业务规则。
15. Mock 测试只证明接口协议、参数序列化与适配器映射逻辑；业务领域行为、多轮交互、LLM Agent 相关动作必须由真实后端集成测试证明。
16. 现行文档只描述当前实现，历史原因和被替代方案统一保留在 ADR。

## 组件与状态层规范

（如与现有 Misskey 基础组件架构冲突，以现有基础组件架构为准。）

1. 区分基础组件与业务组件：基础组件仅接收基础原始类型，不含业务领域逻辑；业务组件接收 domain 权威模型作为 props。
2. 组件 props 只读，禁止组件直接修改传入的领域模型，业务变更必须通过事件提交至 Store Action 处理；组件仅允许保留临时 UI 状态，业务状态统一存放于全局 Store。
3. 仅允许通过 Pinia Store 暴露业务状态，业务组件禁止直接持有业务状态副本，禁止直接消费原始 API 响应作为业务状态。
4. 路由 query / params 仅存放实体标识、分页等简单序列化参数，不得存放完整业务实体，禁止路由成为业务状态副本。

## 附录：与 Misskey 现有架构的冲突裁定

依据"组件 / 状态层与现有 Misskey 基础组件架构冲突时以现有架构为准"的总则：

| 规范条目 | Misskey 现状 | 裁定 |
| --- | --- | --- |
| 组件状态层 #3（Pinia） | 前端未引入 Pinia，使用 Pizzax 自研响应式 store（`store.ts` / `preferences.ts`） | **不引入 Pinia**。Twitter UI 新增业务状态统一经 Misskey 既有 store 机制暴露；禁止为绕开该裁定引入新状态管理依赖 |
| 通用 #5（src-layout 分层） | 既有 `pages/`、`components/`、`ui/`、`boot/` 扁平结构，路由经集中式 `router.definition.ts` 指向 `pages/` | src-layout 分层**只应用于新增的 `ui/twitter/` 模块内部**（domain / adapter / store / components / bootstrap）；受路由与既有组件机制约束的位置（如新页面文件必须位于 `pages/`）遵循 Misskey 现有布局 |
| 通用 #6（index.ts 暴露） | `widgets/`、`components/`、`directives/` 已有 index.ts barrel 先例，但主体为直接文件导入 | 新增模块（`ui/twitter/` 等）对外 API 经自身 `index.ts` 暴露；引用 **Misskey 既有代码**时维持其现有直接导入方式，不为存量代码补建 barrel |
| 通用 #11（Bootstrap 职责） | 已有 `boot/common.ts` / `main-boot.ts` / `sub-boot.ts` 分段引导结构 | Twitter UI 的 readiness / 环境探测消费沿用既有 boot 结构；设备探测等复用 `utility/device-kind.ts`，不得在新组件内自行探测 |

## 补充说明

1. 如果其他领域依赖目前为空，使用空接口 / 空类型占位，避免临时编写跨领域实现。
2. 当前后置完整建设前端交付证明、验收测试部分，但禁止运维探测逻辑侵入 domain 领域模型与业务组件。
3. 复用 Misskey 原有基础组件时，不得修改基础组件内部业务逻辑，业务逻辑封装在业务组件层。
