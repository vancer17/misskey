# ADR-0022：首页时间线手动刷新的查询所有权与结果

## 状态

已采纳（2026-10-22）。

## 背景

首页页头原刷新动作只调用 `MkStreamingNotesTimeline.reloadTimeline()`。该方法将工作交给原分页器，先清空条目与前置队列再请求第一页，没有显式回顶，也没有新增、无新增与失败的结果契约。底层请求失败由分页器捕获，公开的 `Promise<void>` 完成不能作为成功证明。

用户要求显式刷新回顶，并在没有新帖时给出清楚反馈；已有内容应在失败时保留。二次开发约束要求保持共享基础组件内部业务规则，并使事实归唯一查询所有者。

## 决策

1. 为原流式容器增加通用分页器工厂依赖，保留其既有 endpoint / params 映射及订阅、轮询、队列、广告、声音调用。默认消费者仍构造原分页器，不引入架构切换配置。
2. Twitter 首页的业务包装注入专用分页查询所有者，沿用个人主页已有的保留内容刷新模式。所有者复用原分页集合，在刷新成功前保留当前内容，真实适配器保留请求拒绝语义。
3. 手动结果统一为 `updated / unchanged / failed / cancelled`，唯一类型放在 domain。页面只消费结果，不读取 DOM、条目数量或原始 API 响应决定提示。
4. 回顶前记录已展示最大 ID，新增沿用既有时间线游标语义；只声明本次窗口检查结果，不承诺精确新增数量或全局同步。
5. 保留流式组件公开重载入口及其既有副作用。所有者负责请求互斥、归属校验、晚到事件与删除事实；页面负责一次回顶和轻量提示。

## 未采用的方案

- 仅在原 `Promise<void>` 完成后提示成功：无法区别底层失败，且不能保留失败前内容。
- 在页面读取 DOM 或复制列表后判断变化：把渲染投影变为事实来源，且回顶释放队列会污染基线。
- 先查有无新帖，再执行原重载：产生两次请求与时序窗口，仍保留清空集合的失败模式。
- 用普通帖子列表直接替换流式容器：需要重复实现订阅、轮询、队列、声音和广告等原有能力。
- 修改共享分页器的重载算法：扩大对默认界面和全部分页消费者的影响。

## 后果

新增能力位于 Twitter 业务层；共享代码只增加构造依赖接缝、派生类型，以及既有分页尺度与游标的复用入口，不修改原分页算法。最新窗口更新后的分页连续性、失败保留、队列与请求并发需要真实后端回归证明，不能由 Mock 结果替代。

现行契约见 [timeline-refresh.md](../timeline-refresh.md)。
