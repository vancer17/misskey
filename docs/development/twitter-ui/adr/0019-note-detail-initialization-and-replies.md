# ADR-0019：帖子详情初始化、卡片导航与直接回复所有权

## 状态

已采纳（2026-10-22，项目所有者要求按讨论方案实施）。

## 背景

人工核查先发现列表正文无法进入详情，随后发现普通 Chrome 环境经时间戳打开详情出现 `Cannot access 'prefer' before initialization`，无痕模式可以打开。

代码和浏览器检查确认，既有详情路由和页面已存在，时间戳有链接，正文缺少卡片导航。详情和线程使用 `notes/children`，会把直接回复与引用混合，并分别停留在单批 30／10 条。主帖回复动作只打开弹窗，没有原帖下方的内联入口。

独立模块加载暴露静态依赖环：偏好模块经备份工具／同步管理／剪贴板提示进入 `os`，随后经对话框的 Twitter 根 barrel 或页面窗口的路由静态时间线进入帖子捕获模块，最终回读尚未初始化的 `prefer`。只迁移根 barrel 的轻量导入不能切断所有路径。

原用户普通浏览器当时的 HMR、缓存、扩展和资源执行顺序没有完整快照，因此不把具体环境触发因素当成已证实根因。

## 决策

1. 在备份、同步交互和剪贴板提示的实际使用边界延后加载重依赖，保留业务调用条件及剪贴板即时写入时机。分离轻量 Twitter context 公共入口，避免基础展示组件通过业务组件 barrel 形成依赖回路。
2. 复用既有帖子路由，给实际实体卡片补齐正文与空白导航，保持嵌套卡片、文本选择、交互控件以及原链接行为。详情主帖不导航到自身。
3. 由 Twitter 详情包装器嵌入已有表单，仅给基础组件增加展示参数与已有焦点能力。发布、草稿、附件、权限仍由原业务所有者管理。
4. 使用 `notes/replies` 表达直接回复。每个父帖只有一个确认集合，在该查询所有者中实现分页、请求取消和保留窗口刷新，不改变通用基础分页器的业务。
5. 成功回执只用于失效定位，内容和计数重新查询服务端。刷新失败保留原确认内容，隐藏节点不提前加载，卸载后不回填。
6. 已删除 ID 在在途页中可能尚未进入旧集合，故忙碌期间的删除也排队复核。手动刷新与翻页串行，调用者等待真实完成。
7. 通过真实后端验证导航与写入结果；传输延迟／中断只控制网络时序，不伪造业务事实。初始化独立模块实验补充普通启动检查。

## 未采纳方案

- 要求用户清缓存作为永久修复：不能消除静态求值环，也不能证明新用户与其他加载入口稳定。
- 使用 `var`、默认空对象或静默捕获 ReferenceError：隐藏未初始化依赖并改变业务语义。
- 只把整个路由改成懒加载：未覆盖偏好工具的其他回路，还改变已有页面加载策略。
- 重建详情页或自行实现第二份发帖表单：重复既有权限、草稿、附件和创建逻辑。
- 同时保存本地回复列表与分页器集合：引入双重所有权，刷新、删除和分页难以一致。
- 由 `repliesCount` 推断是否还有下一页：计数不等于当前用户可见且通过过滤的查询结果。
