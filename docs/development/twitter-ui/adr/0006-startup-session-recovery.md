# ADR-0006：启动前恢复会话

状态：已采纳。日期：2026-10-15。

当前实现见 [前端启动会话恢复](../session-recovery.md)。

## 背景

浏览器保留的账户凭据被后端拒绝时，原启动链在账户刷新之前就由静态导入创建 Store，并发起账户配置请求。Pizzax 的内部失败未连接外层 Promise，导致启动错误页和悬挂的加载状态。无缓存访问同一实例可以正常启动。

旧恢复路径先等待弹窗，再移除账户或执行普通退出流程。普通退出可能需要云备份并清理整个站点存储，不适合作为失效凭据的最小恢复操作。

## 决策

薄启动入口先通过现有账户接口验证缓存会话，再动态导入主或子启动模块。无缓存直接匿名启动；有效缓存的验证结果替代同次启动中的重复请求。协议适配器不依赖账户单例、Store 或弹窗，账户类型复用 Misskey 权威模型。

明确失效的会话由既有账户模块定向清理，并等待保存记录持久化。暂时网络故障、5xx、账户暂停或权限错误不推断为凭据撤销。恢复前检查请求归属，避免旧响应覆盖其他标签页的新会话。恢复不依赖云备份，不移除无关设置或其他账户。

Pizzax 的请求、映射及缓存写入保持在同一异步链。加载失败立即被观察，但原 loaded 仍拒绝；共享启动消费失败结果，账户向导只在加载成功后启动。

## 未采用的替代方案

仅在 common 中增加 await 不能阻止静态导入时已启动的请求。空 catch 会隐藏失败；仅补 reject 而不处理消费者，会将未处理拒绝转移到下一层。全局屏蔽错误、每次清理全部缓存、自动匿名重放请求、引入第二套状态框架，都不解决本次局部生命周期问题。

## 影响与边界

缓存登录用户的应用导入需要等待一次账户验证；临时故障显示可重试启动状态。现有全局错误兜底保留，不改动页面布局、Nitter 参数、基础组件业务逻辑或后端鉴权。该决策不提供所有业务 API 的透明重试。

行为证明使用隔离真实后端签发及撤销凭据。协议单元测试与传输故障注入不替代真实会话恢复验收。
