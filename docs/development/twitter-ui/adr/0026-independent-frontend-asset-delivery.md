# ADR-0026：主前端与嵌入前端分别选择资源交付方式

## 状态

已采纳（2026-10-23，项目所有者要求修复 `APP_IMPORT`）。

## 背景

成就与通知同步修复的验证过程中，生产主前端构建写入了开发工作区的 `built/_frontend_vite_`。既有后端 watch 随后重启，读取到主前端 manifest 存在、嵌入前端 manifest 不存在的混合状态。

HTML 模板按主前端 manifest 注入生产 hash 入口，但资源服务使用嵌入前端 manifest 的单一条件选择两套资源的交付方式。此时 `/vite/` 被代理到开发 Vite，生产入口 JS 和 CSS 均返回 404，加载器显示 `APP_IMPORT`。清空独立浏览器会话同样复现，排除了开发账户缓存作为必要条件。

此前生产隔离测试同时准备了两套制品，未覆盖这一混合状态；仅检查开发端口仍监听也未证明页面可用。

## 决策

1. `ClientServerService` 分别读取 `frontendManifestExists` 和 `frontendEmbedManifestExists`，为 `/vite/` 与 `/embed_vite/` 独立注册静态资源或既有开发代理。
2. 每个静态分支独立封装去查询参数钩子，避免影响另一套开发代理。保留原上游、端口规则与静态缓存语义，不新增运行时配置或业务架构开关。
3. 新增四种 manifest 组合的真实 HTTP 协议回归，同时验证缓存与查询参数行为。浏览器页面启动使用真实开发地址单独验证，不以构建成功或端口存活替代。
4. 将本次生成的主前端生产制品归档至任务目录，由既有 watch 的一次正常重启重新读取开发状态；不删除开发账户、业务数据或浏览器持久化信息。
5. 后续生产验证使用独立 checkout／staging 和输出目录。开发根目录与验证制品分离，不通过临时修改领域模型、组件、环境配置或加载器错误处理绕过问题。

## 未采用的方案

- 只将统一判断改为主前端 manifest：会破坏“只有嵌入制品存在”的另一种混合状态。
- 屏蔽 `APP_IMPORT` 或增加加载器重试：无法提供实际不存在于开发上游的生产 hash 文件。
- 要求清空用户浏览器缓存或重新登录：不能修复服务端入口与资源来源不一致。
- 在开发服务运行时反复覆盖共享生产目录验证：会再次改变既有 watch 和模板读取到的制品状态。

## 后果与验证边界

两套前端可以独立处于开发或静态交付状态，HTML 与各自资源来源保持一致。四组合测试限定为基础设施协议；业务行为仍由相应真实后端集成测试证明。

当前资源交付及隔离验证要求见 [Web 前端资源交付](../../frontend-assets.md)。本次运行证据位于 `tmp/app-import-fix-20261023/`，以最终测试、浏览器和交付检查结果为准。
