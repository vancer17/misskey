# ADR-0025：本人成就采用唯一业务状态，通知以已确认水位对账账户

## 状态

已采纳（2026-10-23，项目所有者要求实施修复）。替代 ADR-0024 中本人成就继续由原组件私有查询的数据归属决定；Compatible 页面表现、目录和资产规则延续。

## 背景

真实隔离后端复现了两条独立缺口：三分钟申领已在服务端成功，本人成就原组件仍显示先前加载的锁定列表；相同路径命中 KeepAlive 后不重新查询。非实时模式中通知查询已将服务端水位标为已读，账户角标却仍持有旧值。实时前台正常接收到已读事件时角标可消失，不能据此推定所有模式都正常。

原申领 helper 的 Promise 未覆盖 HTTP，原已读端点也未等待水位写入。因此仅在调用后立即重取仍可能读取旧事实。原七个页面用例只证明申领落库、可导航与布局，没有在缓存期间改变事实并要求当前页直接解锁。

项目要求不修改复用基础组件的内部业务逻辑。原 `MkAchievements` 不提供可等待的刷新契约，外部无法可靠协调其私有查询与点击后立即重取；直接增加刷新分支会突破 ADR-0024 的复用边界。

## 决策

1. 新增独立 `achievements/` 业务模块，默认与 Twitter 的本人成就路由共同消费唯一 Store；UI 上下文只决定页面壳与样式，不切换内部业务架构。其他现有消费者继续使用原 `MkAchievements`，本次不扩展这些消费者。
2. 权威目录迁入 domain 并沿用原徽章、名称、时间及文案。旧 utility 导出仅支持实际存量调用点，随这些调用点的局部迁移移除；新消费者使用模块公共入口，不增加兼容能力。
3. 本地真实申领成功、缓存回访、恢复可见及已启用实时模式的成就通知只产生失效意图，查询结果决定成就事实。失败保留旧列表，不以通知或乐观数组补全解锁记录。
4. 后端等待已读水位实际持久化后发布事件并返回 HTTP。原子比较保证并发旧请求不能回退水位，保留原全量已读语义。
5. 通知已读、实时信号和账户通知字段均通过唯一账户对账动作更新；动作读取 `i` 后只提交原账户的两个通知字段。Sidebar 与 MobileBar 保持原读取路径，不新增未读 Store 副本。
6. 请求意图串行合并，按账户、会话及代次拒绝旧响应。已提交的已读操作不因路由离开取消。原通知流的局部标记和后台读取规则保持既有边界，本次不将其当作全局已读来源。

## 未采用的方案

- 随机 key、强制重新挂载、禁用 KeepAlive 或整页刷新：破坏已有缓存与滚动语义，且掩盖失效链缺口。
- 直接给原基础组件增加内部查询／申领逻辑：违反项目明确的复用边界。
- 从通知、旧账户快照或表单反向构造成就记录：形成第二份权威事实。
- 角标本地归零／减一／加一并与 HTTP 快照混用：延迟事件会重复计数，失败或新通知会被错误解释。
- 固定延迟后查询：不能证明服务端写入完成。

## 后果与验证边界

本人成就新增业务容器与只读展示，默认界面的数据链也经过该 Store，因此必须复核默认网格和原资产表现。少量相似展示结构不复制权威目录、解锁事实或业务状态；不建立通用接口层和新的状态框架。

真实后端用例覆盖当前页更新、同路径缓存回访、实时／非实时、服务端水位完成、失败与迟到响应；视觉以同条件前后图复核现有布局。运行结果由最终验证产物记录，不由用例存在推定通过。当前实现契约见 [本人成就与通知账户同步](../achievement-notification-sync.md)。
